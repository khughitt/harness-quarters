The user's ask (relay session, 2026-11-01, while scoping relay-7b8340): "Are the harness hook / relay capabilities documented clearly here or in hq? If not, it would be good to also start to think about creating a capabilities matrix (or matrices if we wanted to split hq vs. relay). Claude Code and Codex should already be covered in such a matrix; antigravity, and later pi, opencode, and crush should be added."

What exists today (agent's survey, 2026-11-01):
- hq facts/capabilities.toml: probed behaviour facts (controller wake, answer routes, MCP stdio, session-start timing, usage reporting, ...; about 26 facts) for agy, claude-code, codex, opencode, pi and pi-durable, each with status, value, conditions and evidence. It is readable only as JSON through tools/harness-facts (check, list, get); there is no rendered table, and it records no hook-event support (which native events fire, what they carry, whether they can refuse or inject context, timeouts).
- relay docs/api.md "Event mappings": native event to relay kind and level for Claude Code, Codex and OpenCode. Reply channels (refuse, context) and outer timeouts per event live only in src/adapters/*.js.
- hq docs/runbooks/adding-a-harness.md: per-harness integration level in prose (which layers each harness gets: homes, skills, hooks, relay).
- Crush appears in no fact or runbook (only obs-175b10 plans to index its sessions).

Open for scoping: one matrix or a split (hq: probed harness behaviour and integration layers; relay: hook events, kinds, reply channels and timeouts it dispatches), whether a rendered table is generated from facts/capabilities.toml and relay's adapter tables or written by hand, and order of coverage (Claude Code and Codex first, then agy, then pi, opencode and crush). Related: relay-67b733 (inventory of duplicated harness assumptions and a shared fact format with two consumers), hq-2eba07 (declarative harness manifest), relay-7b8340 (agy adapter, which adds agy rows and reply-channel columns to relay's Event mappings).
