Why: a controller writing a review-round note for a Codex reviewer needs the model that ran it, and the session-logs skill names no route to it, so the note says harness only or names the wrong model. A Codex rollout carries two model fields. session_meta's base_instructions.provenance.model is the model at creation: for a child, the parent's model at spawn, and stale in top-level sessions after a switch. The last turn_context.payload.model is the model that ran, and children cannot switch model (established by hq-1bd166; lore docs/notes/2026-10-02-codex-model-identity-brief.md §5-§6). On 2026-10-20, 176 of the 400 most recent October rollouts on this host had the two differ (child 01a140a1…: created under gpt-6.1-sol, ran gpt-6-luna). relay model --harness codex answers only for the calling session's own thread (relay docs/api.md, Codex model resolution), so it cannot name a child's model.

Done: agents/skills/session-logs/SKILL.md gains a short "Which model ran" entry with a recipe in the style of its others. It covers four cases. A Codex child: take its thread id (the spawn result, or a hook payload's agent_id), find its rollout under $CODEX_HOME/sessions or archived_sessions (or state_5.sqlite threads.rollout_path), and read the last turn_context.payload.model and effort, never base_instructions.provenance.model. A Codex child's parent: session_meta.payload.source.subagent.thread_spawn.parent_thread_id. The session's own model: $(relay model --harness codex --pretty). Claude Code: the assistant records' message.model. Check: run the recipe on one divergent child rollout and confirm it prints the turn_context model, not the creation-time one.

Where to look: [ref:brief] §2; hq-1bd166's notes; relay docs/api.md. Related, not overlapping: hq-fce47e and lore-f71994 cover a Codex session's own stamp and reviewer identity.
