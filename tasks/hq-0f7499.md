Found while fixing hq-ecee7e (2026-11-09). Once the Sandbox fixture supplies hostkit's work-link config, 45 of tools/test_rename_cutover.py's 180 tests still fail, all with one message: `rename-cutover: guard: <state>/tasks changed outside ai/tack: rename-commit/tack.toml` (hq shape: `rename-commit/hq.toml`). The work-link failure had masked them, since apply stopped before rollback ran.

Cause: tasks commit 98c2383 (feat(lifecycle): preserve retirement and commit completed prefix renames) makes `tasks rename` leave a host-local receipt at XDG_STATE_HOME/tasks/rename-commit/<new>.toml. `tasks commit --project <new>` verifies and commits the rename's paths and removes the receipt (tasks docs/project-operations.md, around line 172). rename-cutover's guard (tools/rename-cutover, def guard) admits only claims/<old|new>.* and rename/<old>.toml as the cutover's own state, so every rollback after a completed `tasks rename` refuses. This is a tool defect, not only a test one: a real rollback with the current tasks binary would refuse the same way.

Questions to settle at scoping: should the guard admit rename-commit/<new>.toml (validated against old/new like validate_inventory does for rename/<old>.toml); should apply's printed records commit (raw git add/commit) become `tasks commit --project <new>`, since a raw commit leaves the receipt behind and a lingering receipt blocks later renames; and whether rename-cutover is still worth maintaining at all after the 2026-10 hq rename it was built for.

Verification: TT_FORCE-free focused run `just test-one tools/test_rename_cutover.py` passes on a host whose work-link is hostkit's.
