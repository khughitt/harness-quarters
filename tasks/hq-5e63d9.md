Why: Codex's request_user_input_async (codex-cli 0.162.1) has no way to withdraw a pending question. In a prism live-measurement run (2026-10-10, ~18:46–19:30Z) the agent asked the user to perform live-run steps through it; once the measurement context was cleaned up, an earlier prompt stayed answerable, so the user could act on a run that no longer existed. This is upstream Codex behaviour: hq can neither add the operation nor intercept the card.

Upstream search (2026-10-11, openai/codex issues and PRs for "request_user_input cancel", "withdraw", "cancel pending question", "dismiss question card", "stale question async", and all request_user_input_async issues): no cancel or withdraw request found. Related open issues are the opposite failure, cards vanishing too early (#43803, #45646, #43057, #48563), plus #44833 and #29104 (blocking questions in default mode).

Done: an openai/codex feature request is drafted that asks for a cancel/withdraw operation on a pending request_user_input_async question (or for questions tied to a turn or context to expire with it), citing the related issues above and following the repository's issue template and contributor guidance; the user has approved or declined publishing it, and the outcome (issue link or decision) is noted here. Until it lands, the workaround is for the agent to say in its next message that the earlier prompt is void and need not be answered.

Where to look: the originating Codex rollout (2026-10-10T14-04-35-01a126fc…, request_user_input_async calls from 18:46Z); openai/codex issue templates. Publishing is an action outside the repository and needs the user's approval.
