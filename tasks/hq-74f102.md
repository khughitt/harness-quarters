Found while fixing hq-0f7499 (2026-11-09). `tasks rename` leaves a receipt at XDG_STATE_HOME/tasks/rename-commit/<new>.toml that only `tasks commit --project <new>` (no targets) consumes. rename-cutover's runbook commit is a raw git commit (apply prints `git -C <records> add -A -- <old> <new> && git commit ...` for a detached checkout; in-tree the checkout is committed by hand), so after a successful forward cutover the receipt stays behind.

Consequences of a leftover receipt (tasks src/commands/commit.rs, src/rename/handoff.rs): every later bare `tasks commit --project <new>`, the documented recovery for a commit_deferred or commit_failed record write, loads the receipt, re-verifies its frozen digests and refuses (`rename receipt digest mismatch`) once anything has changed. A predecessor handoff naming <new> also refuses (`predecessor rename is uncommitted`).

Why it is not a one-line swap: printing `tasks commit --project <new>` in place of the raw commit works for an in-tree checkout, but for a detached one it refuses with `rename receipt digest mismatch: <records>/<new>/tasks/.config.toml`. apply runs `tasks init --prefix <new> --records <root> --force` after moving the checkout, which rewrites the config's [checkout] path, and the receipt froze the pre-move config digest. Tried in .worktrees/hq-0f7499 and reverted; 16 detached tests failed that way.

Options to weigh: (a) apply runs `tasks commit --project <new>` itself right after `tasks rename`, before the move, then prints a second scoped commit for the config init --force rewrote; this changes the 2026-11-02 detached design's contract that apply prints and the runbook commits, and changes where a hook refusal stops apply; (b) tasks lets the documented post-move `init --force` refresh a pending receipt's config digest, so the printed commit can be `tasks commit --project <new>` (filed as tasks feedback, see notes); (c) verify refuses while the receipt remains, naming the command, once (a) or (b) makes it clearable.

Outcome: after a forward cutover, no rename-commit receipt for <new> remains on the host, and verify says so. Verification: the whole-cutover tests (in-tree and detached) assert the receipt is gone after the runbook commit.
