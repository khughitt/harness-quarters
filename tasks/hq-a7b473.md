Why: `just test`'s parallel relay-cutover segment went red on unchanged sources at load ~98 on 32 CPUs (387 passed, 2 failed); both cases pass serially (2 passed in 168.84 s). A suite that fails under load is not a usable gate. Fix the tests' dependence on wall-clock timing without weakening cancellation or service semantics.

Original report (agent-observed, codex): test_recovery_signal_is_retried_by_reconciliation received `failed` where it expected `interrupted`; test_partial_finish_keeps_original_timers hit a service-start failure where it expected `still activating` under its 0.3 s budget. No verbatim failure text was retained (verification summary under $WORK_ROOT/hq/hq-268cc2/).

1. Service-start bound (established by reading, same mechanism as hq-38e479). restoration.service_run bounds the `systemctl --user start` child with SERVICE_SECONDS, the same constant that bounds the settle wait in _settled. The tests shrink that one budget (0.3 s here, 0.2 s in test_service_run_wait_and_result) to reach "still activating", so under load the fixture's start shim itself overruns and is stopped. Fix: give the start child its own bound (SERVICE_START_SECONDS, equal to SERVICE_SECONDS in production, so the live deadline is unchanged), carried through the fixture config, so the tests shrink only the settle budget; the fixture's show then reports activating for its whole poll count and the outcome no longer depends on host speed. This also closes hq-38e479.
2. Signal case (mechanism unconfirmed). `failed` at that assertion means Europa's dependency-restore returned a failed response before the SIGTERM reached hosts.request (a signal inside request always yields Interrupted). The leading candidate: the fixture's 20 s sync budget (test_relay_cutover_transport.py World config) expired first, while the sender thread allows 60 s. Fix: give this test a sync budget longer than the sender's window, so only the signal ends the wait, and make the first assertion print failed.error so a recurrence names its cause. Demonstrate the candidate mechanism with a scratch delay of the sender past the default budget (RED), then pass with the fix; state that this shows the mechanism exists, not that it was the one hit under load.

Done: both changes on a branch; `just test` green; the two tests plus test_service_run_wait_and_result pass; the scratch RED/GREEN for case 2 recorded in a note.

Where: tools/relay_cutover_bootstrap/restoration.py (service_run, _settled, _SERVICE_DEADLINE), tools/test_relay_cutover_transport.py (World config, install(), HOST_TIMING), tools/test_relay_cutover_bootstrap.py:3111 and :5565 and the service-run case near :3505.
